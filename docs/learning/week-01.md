# 1주차: 실행하고, 경계를 확인하고, 설명하기

현재 **실제 데이터·학습된 탐지기·실제 성능 결과가 없습니다.** 합성 PGM과
`SyntheticSmokePredictor`는 연결 확인용입니다. 이 주의 목표는 모델 개발이 아니라
자신의 작은 변경과 그 한계를 설명하는 것입니다.

아래 30분 + 2시간 + 30분은 초보자용 **계획 추정치**입니다. 속도 평가나 의무 시간이
아닙니다. 막히면 오류와 시도한 명령을 남기고 범위를 줄입니다. 리더는 아래 네 과제를
분담하고 공유 계약 변경·충돌·최종 통합을 검토합니다. 공개 기록에는 이름·학교·개인 일정,
실제 사진·경로·토큰·가중치를 넣지 않습니다.

## 개념 읽기 — 약 30분

- 10분: [인터페이스](../interface.md)를 읽고 `pixels[y][x]`, score, heatmap,
  provenance, calibration을 한 문장씩 풉니다. score는 확률이 아니고, heatmap은 위치 표시입니다.
- 10분: `src/display_defect_ai/synthetic.py`를 읽습니다. 입력 0.5 → 0,
  0 또는 1 → 1인 `abs(value - 0.5) * 2`를 손으로 계산합니다. 이는 학습이 아닙니다.
- 10분: [데이터 규칙](../data.md)을 읽고 train/validation/test 역할을 구분합니다.
  임계값은 validation에서 고정하며 test 결과를 보고 바꾸지 않습니다. 같은 패널이나
  촬영 세션의 유사 사진을 분할에 섞으면 누출될 수 있습니다.

저장소 루트에서 실행합니다. PowerShell은 먼저 `$env:PYTHONPATH="src"`를 설정하고
명령 앞의 `PYTHONPATH=src`를 빼세요.

```bash
python --version
PYTHONPATH=src python -m unittest discover -s tests -v
PYTHONPATH=src python -m display_defect_ai.cli tests/fixtures/synthetic/bright_patch.pgm
```

foundation 기반 QA 브랜치에서는 25개 중 22개 통과, 3개 예상 실패가 기준입니다.
예상 실패는 고쳐진 버그나 통과가 아닙니다. 이후 core 수정으로 결과가 달라지면
[검토 기록](qa-review.md)과 비교하고 담당자에게 알립니다.

## 작은 과제 하나 — 약 2시간

공통 시간 배분: 환경/명령 20분, 아래 과제 70분, 재실행 20분, 인계 메모 10분.
각자 하나만 선택합니다. 새 테스트나 학습 메모 안에서 작업하고 모델·데모·공유 계약은
리더 검토 없이 바꾸지 않습니다. 추가 패키지·실제 데이터·GPU는 필요 없습니다.

| 과제 | 제한된 작업 | 완료 증거 |
|---|---|---|
| 입출력 읽기 | 기존 합성 CLI JSON을 읽어 필드 6개를 학습 메모에서 설명합니다. 미보정·위치 정보 없음일 때 표시할 문구를 각각 작성합니다. GUI는 만들지 않습니다. | 실행 명령, 예상 문구, score를 확률이라 부르면 안 되는 이유 |
| QA 경계 하나 | 새 테스트 파일에서 `heatmap=None`인 3×2 결과를 JSON으로 왕복시키고 크기·null·미보정 상태를 확인하는 테스트 하나를 작성합니다. | 실행 결과, 예상 값의 이유, 다른 사람의 재실행 |
| 데이터 분할 연습 | 실제 파일 없이 가상 ID 6개와 가상 패널 그룹 3개를 표로 만듭니다. 같은 그룹이 분할을 넘지 않게 배치하고 실제 평가 가능 여부를 설명합니다. | 가상임을 표시한 표, 그룹 중복 검사, 표본 부족/라벨 부재 한계 |
| 재현·발표 연습 | README 명령을 따라 실행하고 Python 버전·커밋·명령·결과·미실행 항목을 한 페이지로 기록합니다. | 타인이 따라 할 수 있는 메모, 성공과 예상 실패를 구별한 숫자 |

가상 데이터 표나 단위 테스트 threshold는 실제 데이터·보정 결과로 보고하지 않습니다.
계약이 이상해 보여도 테스트 기대값을 구현에 맞춰 조용히 바꾸지 말고 작은 재현을 남깁니다.

## 설명과 교차 확인 — 약 30분

10분은 다른 담당자가 명령을 재실행하고, 10분은 아래 질문에 답하고, 10분은 리더에게 인계합니다.

1. 입력은 어디서 왔고 합성이라는 근거는 무엇인가요? marker는 진위를 인증하나요?
2. 바꾼 줄의 입력·출력·실패 조건을 예 하나씩 설명할 수 있나요?
3. threshold와 같은 score는 왜 anomaly인가요? calibration이 없으면 왜 미보정인가요?
4. 테스트 통과가 실제 결함 탐지 정확도를 뜻하지 않는 이유는 무엇인가요?
5. test를 보고 threshold를 고르면 어떤 정보가 새어 나가나요?

인계에는 변경 파일, 커밋, 실행 명령, 통과/실패/예상 실패/미실행을 따로 적고
모르는 점 하나를 남깁니다. AI가 쓴 코드도 사람이 기대값을 독립적으로 계산하고
재현해야 합니다. AI 설명이나 테스트 개수로 정확도·재현율·공장 적용 성능을 만들지 않습니다.
